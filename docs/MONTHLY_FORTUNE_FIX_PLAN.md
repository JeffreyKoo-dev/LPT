# 이번 달 운세 월 보정안 (2026-10-28)

## 1. 문제
`calculateMonthlyFortune()`은 달력의 N월을 사주의 N번째 절기월(1번째=인월, 입춘 무렵 시작)에 그대로 대응시킨다 (`result.wolun.find(item.month === 달력월)`).
사주의 월은 절기로 나뉘므로 달력월과 약 한 달 어긋난다.

### 검증 (엔진의 절기 계산으로 2026-01-01 ~ 2027-12-31, 730일 비교)
- 현재 방식이 가리키는 월건(월의 간지)이 정답과 다른 날: **730일 중 730일(100%)**. 십성 조합도 100% 다름.
- 예) 2026-10-27: 정답은 술월 戊戌(10/8 15:30 ~ 11/7 18:51 KST), 현재 방식은 해월 己亥(다음 절기월).
- 절기월 경계(KST, 2026): 1/5 17:19, 2/4 04:55(입춘), 3/5 22:50, 4/5 03:28, 5/5 20:36, 6/6 00:37, 7/7 10:49, 8/7 20:40, 9/7 23:41, 10/8 15:30, 11/7 18:51, 12/7 11:49.
- 즉 매달 1일~절기일(대략 3~8일)은 두 달 어긋나고, 이후는 한 달 어긋난다.

### 영향
- AI가 받는 월운 데이터(간지·십성·12운성)가 해당 시기의 것이 아니다. 결과 문장이 일반적인 톤이라 체감은 어렵지만, "이번 달의 흐름"이라는 상품 설명과 데이터가 어긋난 상태다.
- 상품 설명과 실제 내용이 다를 때의 환불·청약철회 문제는 법률 검토 사항이다(자문 아님).

## 2. 선택지
| 안 | 내용 | 평가 |
|---|---|---|
| A. 생성 시점의 절기월 1개 사용 | 구매·생성한 날이 속한 절기월 데이터로 작성 | 한 달 동안 캐시되므로 월 중반에 절기월이 바뀌면 틀린 내용이 남는다. 비추천 |
| **B. 달력월을 절기월 구간 2개로 나눠 제공 (추천)** | "월초~N일(절기)은 X월, 이후는 Y월"을 함께 주고 AI가 전반부/후반부로 풀이 | 달력월 구매 방식(이번 달 1회)을 유지하면서 데이터가 정확하다. 한 달 캐시와도 맞다 |
| C. 상품을 절기월 단위로 판매 | "10/8~11/7" 식으로 기간 표시, 절기일에 리셋 | 가장 정확하지만 구매 주기가 낯설어 이해하기 어렵다 |

## 3. 추천안(B) 구현 계획
1. **엔진**: `getSajuMonthSegments(year, month)` 추가. 이미 있는 `resolveNearestMajorSolarTermUTC`로 그 달의 절기 시각(KST)을 구하고, 월초 구간·월말 구간의 (입춘 기준 사주 연도, 절기월 번호)를 계산. `calculateWolun(sajuYear, 일간)`으로 각 구간의 간지·십성·12운성을 만든다. 1월(자월→축월, 입춘 전이라 전년도 기준), 2월(축월→인월, 연도 전환)을 반드시 별도 시험.
2. **데이터 타입**: `MonthlyFortuneData`에 `segments`(구간 이름, 시작·끝 날짜/시각, 간지, 십성, 12운성) 추가. 기존 필드는 더 긴 구간 기준으로 유지(호환).
3. **Edge Function 프롬프트**: 구간 두 개를 알려 주고 "월초~N일", "N일 이후"로 나누어 5~9문장으로 작성하게 한다. 이름표 없이 이어지는 글.
4. **캐시 무효화**: 콘텐츠에 `version: 2`를 붙이고 version이 없는 기존 이번 달 캐시는 무효 처리. 이미 이번 달 결제한 사용자는 재결제 없이 보정된 내용으로 다시 생성한다(카드의 생성 버튼).
5. **검증**: 임의의 날짜 D에 대해 `calculateSaju`가 계산하는 **월주(그 날 태어난 사람의 월 기둥)**와 구간 간지가 같은지 전수 비교(독립 검증). 730일 전부 일치해야 한다.
6. **배포**: 패치 + Edge Function 재배포. SQL 없음.
7. **안내**: 이미 구매한 사용자에게 별도 공지는 필수 아님(재생성 가능). 필요하면 앱 내 한 줄 안내.

## 4. 일정·우선순위

- 사용자가 많지 않은 지금이 보정에 부담이 가장 적다.
